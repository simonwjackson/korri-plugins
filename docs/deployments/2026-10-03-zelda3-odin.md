# Zelda3 fullscreen defaults on the Odin 2 Portal

On 2026-10-03, the owner changed the validation target from Mini V2 to Odin and said, "device is yours. go". The signed ARM64 Zelda3 plugin is installed and enabled. Fresh and cached native launches rendered the Zelda intro at 1920x1080 without a game-window focus command.

**Verification limit:** Odin's Chromium portal repeatedly crashed after the catalog reload. The successful cold and cached tests temporarily stopped that service. The service was restarted afterward, but its crash remains unresolved. This verifies native fullscreen startup, not stable coexistence with Odin's portal or the original hidden-window condition.

## Package correction and build checks

`plugins/zelda3/package.nix` patches only the packaged upstream INI's `[Graphics] Fullscreen = 0` to `1` with `--replace-fail`. This is upstream's desktop-fullscreen mode. The native launcher already copies defaults only when the account INI is absent. Existing windowed choices remain unchanged. The `Alt+Return` toggle remains available.

The added regression failed against the old package with `Fresh installs must request desktop fullscreen`. Package, contract, admission, sandboxed callback and ROM-free runtime checks passed on x86_64 and aarch64 after the fix. Owned-ROM checks also passed on both architectures, including cold extraction, cached launch, save/reload and preservation of an explicit windowed choice. These are build-machine results, not physical-controller or speaker tests.

Before the rebased ARM check, a read-only monitor waited for Fuji's existing compiler jobs. Two probes 30 seconds apart showed no build processes and CPU use of 5.0%, then 4.2%. Only then did the ARM check run. Final checks passed again after another rebase, using the same immutable check derivation and plugin output. No target-device build or flake evaluation ran.

The cost of the correction is fullscreen startup on desktop Linux too. The user can edit the native INI to choose windowed startup. This does not solve the portal's Chromium crash or silently change older account configurations.

## Portal crash and test isolation

The initial probe found a visible portal window and no game. After catalog reload, `korri-chromium-kiosk.service` repeatedly restarted Chromium. Coredump metadata identified `SIGSEGV`. One explicit portal restart did not restore a stable window.

A reversible baseline test restored the preserved pre-Zelda3 catalog, device configuration and private discovery state. The portal still failed to present a window. The current catalog was then restored. This rules out the added game record as a sufficient explanation; it does not establish the crash's cause.

With the restarting portal present, two cold-launch tests saw Zelda3 become fullscreen, then lose Sway's fullscreen flag while remaining visible, focused and 1920x1080. One cached diagnostic launch stayed fullscreen. After only the crashing portal service was stopped, both cold and cached fullscreen assertions passed. This is consistent with interference from the portal restart loop. It does not prove the exact window-manager sequence.

The portal service was started again after testing. No browser arguments, credentials, trust, compositor policy or global settings changed. The final probe observed the portal starting with no stable window. There were no terminal failed units at that instant, which does not prove that the restarting portal works. Repairing that crash remains a separate task.
